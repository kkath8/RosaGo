# Phase 2E — required qualification and production acceptance

**Plan only. No tests against production are authorized or performed here.** All destructive fault injection, clock changes, restore/replay, OOM, membership changes, credential rotation and provider-policy experiments belong in isolated staging. Use synthetic or explicitly authorized test accounts, a dedicated namespace/service and no production secrets.

The production startup safeguard stays active through corrective implementation and isolated qualification. A future release review must explicitly approve activation; changing the mode to development or redis-local is never an acceptance workaround.

## Evidence prerequisites

Record the exact source/dependency/script versions, root HTTPS origin/proxy topology, worker count/concurrency, compatible schema/key IDs, external gate generation and realm epochs, provider/primary-incarnation policy, retention/memory/connection envelope and rollback release. Use at least two actual WSGI worker processes with no stickiness and real HTTP/browser requests through the intended reverse proxy.

Generate test encryption material in the secret manager or ephemeral isolated fixtures. Evidence records counts, gate state, worker labels and non-secret version IDs; never passwords, raw session handles/cookies, bearer/refresh credentials, OTPs, PKCE verifiers, key material or authenticated Redis URLs. Scrub traces and local variables as well as request logs.

## Controlled production acceptance after separate approval

Production acceptance begins only after infrastructure and release activation approvals, completed staging gates, authorized A/B credentials and an agreed stop/rollback owner. Do not change memberships/provider policies or force faults on production to manufacture negative cases.

1. With the public auth gate still closed, an authorized operator verifies the approved writer/generation/epochs, private TLS, ACL/configuration evidence, both realm readiness paths, secret versions and exact HTTPS/proxy/root/cookie setup. Do not print connection strings or keyring contents.
2. Open the limited approved scope. In one browser context sign in A on User, B on Admin, verify identities across workers and repeat in reverse order. Check desktop/mobile navigation and callback/origin behavior.
3. Logout A and verify B, then logout B and verify A. Replay only those approved test handles in the controlled acceptance harness without recording them in reports. Verify independent expiration/reauthentication using approved test sessions; avoid disruptive live clock or membership changes.
4. Use permitted nonmember and wrong-CSRF cases with the authorized test accounts; verify denial and no business writes. Check that a token supplied by one realm cannot authorize the other.
5. Exercise approved recovery/verification/account flows only for the authorized accounts and intended email recipients. No email or recovery request is sent by this review. Confirm other-realm preservation and secret-free evidence.
6. Observe qualified metrics, both worker readiness and no cross-cookie contamination. Do not claim the failover gate passed from an uneventful observation window; its failure qualification belongs to staging.
7. Read-only Admin/User destination/photo/Environment checks must preserve current records, statuses, timestamps, audit history and Storage objects. A session rollout must not toggle Environment or alter data contracts.

An actual production audit-row proof is **separate**: Phase 1D remains deferred. It requires renewed explicit approval, working authorized write access, fresh preservation checkpoints and exactly the approved new disposable Draft. Never use Chowking or another existing destination, publish the Draft, upload/delete Storage, or delete audit history. Draft-only testing cannot prove positive public visibility synchronization. Without that authorization, report production audit insertion as unverified while retaining the isolated contract evidence.

## Stop and sign-off

Immediately close the affected auth scope on cross-realm identity, first-request stale authority after restore/promotion, wrong actor, duplicated provider write/refresh, unsupported writer switch, unbounded state growth, failed preservation check, secret leakage or ambiguous business mutation. Do not automatically retry a create/reset/exchange. Reconcile, fence and use the reviewed rollback/maintenance path.

The release record must name each gate PASS/FAIL, evidence location, configuration/code versions, qualified load and accepted fault model, approval owner, cutover/reauthentication impact, rollback release or maintenance fallback, and all remaining unverified behavior. The production safeguard may change only under a separate explicit activation approval; this review does not grant one.
