# Phase 2G — proposed operating contract and recovery rehearsal

This is a proposed procedure, not permission to provision, deploy, change production sessions or run production commands. The lab exercised the control-state/epoch portion only. Actual target-platform cutover, backup restore and rollback remain unqualified. Follow the Phase 2C acceptance scope and the Phase 2E gates; keep the production startup safeguard enabled.

## Required infrastructure and configuration

| Component | Required contract before production approval |
| --- | --- |
| Revision authority | Independently administered transactional/consensus metadata service, verified mTLS, linearizable CAS/read, bounded deadlines, per-realm credentials and operator-only control; not the same host/snapshot/admin domain as Redis. |
| Restore freshness | Non-restored generation/epoch anchor; never-reused epochs; old generations cannot be reopened by a restored service or a freshly started worker. Separately reviewed recovery/operator permissions and audit evidence. |
| Redis | Private TLS with CA/hostname verification, exact realm key/command ACLs, primary-only access, noeviction, explicit memory/connection limits and headroom, qualified persistence/volume/restore behavior. No transparent promotion before an enforceable pre-use gate. |
| Workers | Explicit mode, namespace/protocol/realm epochs/keyring IDs, post-fork per-worker pools, no auth stickiness requirement, no development/memory fallback and no inherited sockets. Production implementation remains absent. |
| HTTPS | Canonical HTTPS origin, exact trusted hosts/proxy-hop count, ingress strips client forwarding headers, workers private, root-mounted routes, Secure host-only HttpOnly/Lax cookies. |
| Secrets | Secret-manager references for Redis/authority workload identities and AES keyring; separate operator identity; least privilege, audit, recovery and rotation. Never put secret values or credential-bearing URLs into this document. |
| Budgets | Forecast sessions and all auxiliary families, pre-auth flood limits, per-family size/count limits, authority map/journal/tombstone bounds, worker/pool totals, memory/RSS/AOF/replication headroom and measured sustained SLOs. |
| Time | Synchronized workers/Redis/authority; measured error bounds; reject out-of-window and stale snapshots. Total request/provider/authority deadlines and independent watchdogs for hung fsync/network operations. |

Existing local inputs include `ROSAGO_AUTH_MODE`, `ROSAGO_SESSION_NAMESPACE`, `ROSAGO_SESSION_AUTHORITY_PATH`, `ROSAGO_SESSION_KEYRING`, `ROSAGO_USER_SESSION_EPOCH`, `ROSAGO_ADMIN_SESSION_EPOCH`, `ROSAGO_PUBLIC_ORIGIN`, `ROSAGO_TRUSTED_HOSTS`, `ROSAGO_PROXY_HOPS` and `ROSAGO_PROXY_HEADERS_SANITIZED`. Their local semantics are not a production backend. `ROSAGO_LOCAL_HTTPS_QUALIFICATION` must not be used to bypass production mode. The current production guard must still reject activation. Authority endpoint/TLS/secret references, a protected control descriptor and operator readiness protocol require separately reviewed implementation; do not invent working production environment switches.

Monitor redacted aggregate storage errors, conflicts, rejected admissions, uncertain refreshes, failover-generation mismatch and control state; Redis RSS/used_memory, eviction (must stay zero), maxclients/rejected connections, latency, AOF/replication/volume health; authority quorum/commit latency, disk/quota, journal/backup integrity and clock bounds. Alert independently when the app cannot reach monitoring. Deliver and acknowledge test alerts; an INFO sample is not alert qualification. Never log cookies, raw session references, JWTs, refresh tokens, verifiers, OTPs, key material or request bodies.

## Recovery from uncertain Redis or authority state

1. **Close admission and protected dispatch independently.** Set the protected control plane BLOCKED; if that control plane is unavailable or freshness is uncertain, ingress and every worker must deny authority. A reachable Redis is insufficient. Liveness may remain healthy while authority readiness returns 503. Keep explicitly stateless public/static routes available only where they require no fallback identity.
2. **Fence/drain old work.** Remove old auth workers from ingress, stop new login/recovery/refresh transitions, fence their generation at the authority service and wait for bounded in-flight operations. A provider or destination mutation already dispatched may have succeeded. Reconcile without automatic replay or claims that logout recalled an already issued JWT.
3. **Preserve incident evidence.** Retain redacted writer/control/version, clock, AOF/manifest, volume, replication and authority history under protected operator access. Do not flush Redis, erase audit history or restore business data to repair sessions. A lost cache record with valid metadata is an outage, never permission to relax digest/revision validation.
4. **Establish a fresh recovery generation.** With a non-restored anchor and authorized operator quorum/process, select a known writer, advance generation and affected realm epochs to never-used values. Shared uncertain restore normally invalidates both realms. If the anchor itself cannot be proven current, remain BLOCKED; do not trust a matching pair of old stores or reconstruct freshness from old snapshots.
5. **Rebuild session authority, not accounts.** Do not import old credential/browser/challenge/refresh/grant references as live authority. Reconcile old generation metadata only for investigation/retention. Preserve business records, photos, Environment, publication state and audit logs. Do not delete/recreate Supabase accounts or change provider authentication settings.
6. **QUALIFYING with traffic still closed.** Start compatible workers with the exact approved descriptor/key IDs and private endpoints. Check TLS/ACL/host/proxy, authority/Redis revisions and clocks, bounded capacity, fresh synthetic auth in an explicitly isolated test namespace, and stale-generation denial. No production test account/namespace is implied by this procedure.
7. **Conditionally OPEN after approval.** Require the latest operator serial/descriptor; stale operator updates fail. Every existing worker must reject old epochs. Require deliberate User and Admin reauthentication and restart in-progress recovery/verification flows with new codes/links. Do not silently convert old cookies or resurrect their state.
8. **Observe and stop on ambiguity.** Confirm both realm identities, independent logout/CSRF, recovery and membership behavior, then monitor error/latency/quota. Any resurrected authority, unexpected actor or ambiguous business mutation closes the gate and requires reconciliation.

Only steps involving the lab witness state, old/new descriptors and fresh synthetic login were exercised. No operator-controlled production service, independent anchor, actual snapshot restoration of that service or production drain was available.

## Proposed cutover rehearsal

1. Select an actual isolated target topology, supported Redis/client versions, independent authority service, protected secret delivery and compatible rollback build. Close all eight gates in REPORT.md before requesting release approval.
2. Reproduce the Redis restart failure with retained disposable artifacts, establish a cause and pass repeated intact-restart tests for credential/browser/CSRF/recovery/verification/rate families and deadlines. Do not proceed based on PING or AOF configuration alone.
3. Run at least two real target WSGI workers without stickiness, private direct-worker ingress, actual HTTPS/proxy and a real browser. Exercise both login orders, both independent logouts, expiry/revoke, cross-CSRF, duplicate/malformed cookies, denied member and recovery/verification on different workers. Provider identities must be isolated/authorized; no production credentials in fixtures.
4. Exercise authority outage/inconsistency/old backup, quorum/writer changes, old-worker rejoin, Redis restart/old replica, disk/OOM/eviction/connection faults, clock steps and delayed responses. Prove no old generation is accepted, including by a newly booted worker with an old local descriptor. Run sustained capacity, alert delivery and restart/rotation tests at the approved limits.
5. Announce the initial sign-out boundary. Old process-local/signed-cookie authority cannot migrate seamlessly. User browser preferences may reset; accounts and business data persist. In-progress login/reset/verification may need a new flow. Do not promise seamless continuity across uncertain restores or incompatible keys/schema.
6. During the later approved cutover, gate/drain the old release, reconcile in-flight work, use new protocol/generation/realm epochs and start the complete compatible fleet. Do not mix old Admin shared-cookie authority with independent sessions or use memory mode.
7. Check readiness and limited approved account acceptance before expanding traffic. No destination mutation is part of this authorization. An actual Admin audit-write proof still requires a separately approved disposable Draft and fresh preservation checkpoints; Phase 1D remains deferred.

## Rollback rehearsal and stop conditions

Prefer a previously qualified independent/shared-store release that reads the active protocol, epochs and keyring. Test this rollback pair in isolation before cutover. If no compatible release exists, serve maintenance for authentication/Admin routes, not the legacy shared-cookie Admin path or development mode. Gate and drain before replacing workers; never automatically repeat uncertain provider/database operations.

If authority, keys or schema cannot be safely retained, advance the protected generation/epochs and require sign-in/recovery restart. Do not roll back epochs, restore old live sessions, globally flush Redis, change production database records, remove Storage objects, delete audit history or change Environment flags. Retain decrypt-only predecessors only under approved bounded retention; emergency compromise recovery may require immediate invalidation rather than compatibility.

Before reopening, repeat stale-cookie/generation denial, independent A/B login/logout, cross-CSRF, denied membership, recovery, actor attribution against isolated fixtures, readiness and actual cookie/proxy checks. Any cross-realm identity, replayed revoked state, unsupported authority freshness, unknown Redis loss, wrong actor, unexpected business mutation or unexplained preservation mismatch is NO-GO. The available local witness is not an approved rollback or production authority target.

## Reproducing local evidence

The lab is destructive only to its own labelled disposable Redis container. Review `run_qualification.py` and helpers before running it. It needs the existing local venv dependencies, Docker Desktop, an available Redis 7.4.7 image, free loopback ports 16389/15443/5131/5132/5443, and writable OS temporary storage outside OneDrive for LMDB. It generates ephemeral secrets, imports no `.env`, mocks providers and leaves production startup disabled. Do not substitute production endpoints or credentials.

The runner saves safety assertions separately from operational findings. A completed run or a safety PASS does not mean persistence passed; inspect `operational_findings` and `restart-diagnostic.json`. Windows PowerShell native stderr handling can mark normal Werkzeug logs as shell errors; use a subprocess capture wrapper if a distinct native process exit status is required. Offline `verify_evidence.py` performs no network or application import and can be rerun to check archived fingerprints and pytest XML. It does not qualify any live infrastructure.
